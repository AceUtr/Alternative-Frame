# 需求拆解与验收条件

## 1. 任务定义

原始任务：**拆解需求并生成验收条件**。

本次输入未包含具体业务需求、用户角色、业务流程或非功能指标，因此本文件将原始任务解释为一个“需求分析交付能力”要求：接收一项待分析需求，输出可追踪、无歧义且可测试的需求陈述及对应验收条件。

## 2. 范围

### 2.1 范围内

- 记录原始需求及其上下文。
- 将原始需求拆分为独立、可验证的原子需求。
- 为每条需求分配唯一标识。
- 为每条需求给出可执行或可人工判定的验收条件。
- 标记输入缺失造成的假设、歧义和风险。
- 建立原始需求、拆分需求与验收条件之间的追踪关系。

### 2.2 范围外

- 推断未提供的具体业务规则。
- 编写产品代码或自动化测试代码。
- 决定需求优先级、上线日期、预算或实现技术方案。
- 在缺少利益相关方确认时，将假设视为已确认需求。

## 4. 验收条件

### AC-001：原始需求可追溯

- **关联需求**：REQ-001
- **前置条件**：已提供原始任务“拆解需求并生成验收条件”。
- **当**：审查本分析文档的“任务定义”章节。
- **则**：该章节包含原始任务原文，且未改变其意图。

### AC-002：需求已原子化并唯一编号

- **关联需求**：REQ-002、REQ-003
- **前置条件**：打开“原子需求”表。
- **当**：逐行检查需求并统计 ID。
- **则**：每行只包含一个可独立判定的义务；所有 ID 均符合 `REQ-[0-9]{3}` 格式且互不重复。

### AC-003：需求陈述明确

- **关联需求**：REQ-004
- **前置条件**：存在原子需求列表。
- **当**：逐条审查需求陈述。
- **则**：每条陈述均包含规范性约束词“必须”或“不得”以及可观察的行为或结果；不存在未定义阈值的模糊质量词。

### AC-004：必须级需求均有验收条件

- **关联需求**：REQ-005
- **前置条件**：原子需求和验收条件均已编号。
- **当**：按追踪矩阵核对所有优先级为“必须”的需求。
- **则**：每条必须级需求至少映射到一条 `AC-[0-9]{3}` 验收条件。

### AC-005：验收条件可判定

- **关联需求**：REQ-006
- **前置条件**：存在验收条件列表。
- **当**：逐条检查验收条件。
- **则**：每条验收条件均明确写出“前置条件/当/则”，且不依赖审查者主观选择即可得到通过或失败结论。

### AC-006：未知信息未被伪装为事实

- **关联需求**：REQ-007
- **前置条件**：本次未提供具体业务上下文。
- **当**：审查“假设、待确认项与风险”章节。
- **则**：该章节明确指出缺失的业务对象、用户角色、业务规则及非功能指标，并将任何临时解释标为假设。

### AC-007：双向追踪完整

- **关联需求**：REQ-008
- **前置条件**：存在追踪矩阵。
- **当**：分别从需求列和验收条件列进行核对。
- **则**：REQ-001 至 REQ-009 均至少出现一次，AC-001 至 AC-008 均有一个或多个来源需求，且矩阵中不存在未定义 ID。

### AC-008：交付物已持久化

- **关联需求**：REQ-009
- **前置条件**：工作区可访问。
- **当**：读取 `docs/requirements-analysis.md`。
- **则**：文件存在、可读取，并包含“任务定义”“原子需求”“验收条件”“追踪矩阵”“假设、待确认项与风险”五部分。

## 6. 假设、待确认项与风险

### 假设

- 本次交付目标是生成需求分析文档，而不是实现新的运行时代码。
- `requirements_written` 表示：拆分后的需求及验收条件已写入工作区中的持久化文件。
- 中文 Markdown 是可接受的交付格式。

### 待确认项

1. 需要分析的具体业务需求是什么？
2. 目标用户或系统主体是谁？
3. 是否存在必须遵循的需求模板、合规标准或优先级规则？
4. 是否要求将验收条件进一步转换为自动化测试用例？
5. 是否存在性能、安全性、可用性等量化门槛？

### 风险

- **业务范围风险**：由于没有具体业务需求，本文件只能定义通用的需求分析交付标准，不能替代业务需求规格说明。
- **验收深度风险**：当前验收以文档检查为主；在补充业务需求后，应增加业务流程、异常路径、边界值和非功能验收条件。
- **假设偏差风险**：若 `requirements_written` 具有项目特定含义，需要由需求方确认并据此修订。
