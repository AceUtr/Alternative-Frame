# v0.1 项目管理与冻结记录

## 1. 版本定位

`v0.1` 是 Alternative-Frame 的基线验证版本，目标是证明合同驱动的多 Agent 长程执行闭环能够运行，并为后续 `v1.0` 提供可回溯的工程基线。

本版本不宣称已经完成真实多设备端边云部署、自由拓扑群聊或任意软件需求自动化。

## 2. 已冻结的核心范围

- 主 Agent 规划、拆解、调度和汇总。
- 子 Agent DAG 依赖、并行执行、任务级重试和阶段级重规划。
- 合同生成、硬证据验收、状态/事件记录。
- 科研与软件工程两个离线领域 Demo。
- 本地 Stub 与 OpenAI-compatible API 模型适配。
- 中心化、有界的 Top-k 稀疏通信 MVP。
- 端边云单机运行时模拟。

## 3. v0.1 验收门禁

每次修改进入下一版本前，至少记录以下证据：

1. Python 编译检查通过。
2. 全量测试结果及测试环境。
3. 科研、软件、端边云、评测四个模块门禁结果。
4. 两个 Demo 的运行 ID、最终状态和产物目录。
5. 失败、重试、局部恢复或重规划场景的事件证据。
6. API 模式下明确记录模型、接口地址（脱敏）和 Token 可用性；不得把密钥写入仓库。

## 4. 目录与产物规则

- 源码、测试、文档和示例进入版本目录。
- `runs/`、缓存、临时测试目录和本地密钥属于运行时数据，不作为版本源代码。
- 正式产物应包含 `manifest.json`、`state.json`、`events.jsonl` 和文件哈希。
- 任何“完成”结论必须由工具调用、退出码、实际文件或指标等证据支持，不能只依据 Agent 文本。

## 5. 变更流程

1. 先在 v0.1 记录问题、影响范围和验收条件。
2. 修改后先跑针对性测试，再跑四个模块门禁。
3. 通过后在 `v1.0` 或后续版本建立清洁快照，不覆盖 v0.1。
4. 若验证失败，保留失败证据并回到最后一个通过的版本；不删除运行记录来掩盖失败。

## 6. 主要风险

| 风险 | 当前边界 | 控制措施 |
|---|---|---|
| CCswitch 不返回 `usage` | Token 可能为 unknown | 记录原始响应能力，使用本地估算和供应商账单对账 |
| 网络/API 不稳定 | 真实模型不适合作为唯一现场路径 | 离线 Demo 作为主演示，API 作为补充 |
| 端边云没有真实设备 | 当前是单机模拟 | 先做多进程/容器网络验证，再申请真实设备测试 |
| 自由拓扑通信复杂度高 | 当前仅 Top-k 中心化路由 | 先保持接口兼容，按阶段增加邻居发现、租约和故障恢复 |
| 运行副本混用 | 可能启动旧 UI 或旧压缩包 | 每个版本保留启动说明、版本标识和清洁快照 |

## 7. v1.0 进入条件

`v1.0` 不是简单改名。至少应完成：清洁快照、版本说明、可复现启动命令、四门禁结果、双 Demo 证据索引，以及对“模拟实现/真实部署/未完成项”的明确区分。
