# Alternative-Frame 双机动态故障恢复操作手册

适用于复验包 `双机复验-831a10b.zip`，固定源码提交：`831a10b980f0de8bdb6ac4009bc373b66daebbf2`。

## 本次要验证什么

主控电脑 A 正在执行任务时，独立注入器会终止 A 上的 Cloud worker。框架应感知通信故障，将同一任务交给另一台真实电脑 B 上的 Edge worker；随后自动完成第二阶段并生成最终报告。

Edge worker 只对任务数据计算 SHA-256，不运行语言模型，也不调用真实 API。本次实验不消耗 API token。它验证动态节点故障后的跨机回退和证据链，不代表任意 API 长程任务都已具备可靠性。

## 准备

1. 准备两台真实不同的 Windows 电脑：A 是你的主控电脑，B 是同学的电脑。
2. A、B 需要通过可互相访问的局域网或组网 VPN 连接。不要把服务暴露到公网。
3. 两台电脑均需安装 Python 3.10+ 和 Git for Windows。不需要安装 Python 第三方包，也不需要连接 GitHub。
4. 将同一个 ZIP 文件分别交给 A、B。两边都用资源管理器右键 ZIP，选择“全部解压缩”，解压到各自独立的文件夹。不要只复制 ZIP 里的部分文件。
5. 不要修改 `test_config.json`。它包含这次实验的 run ID 和临时测试认证值；两边必须保持完全一致。它不是供应商 API key。

复验包 SHA-256：`829eb065b148188cfb8e6289237e37dc29500fec948bbd2f06072838eca49bab`。

## 第一步：两台电脑检查环境

A、B 分别打开自己解压后的文件夹，双击 `00_check_environment.bat`。等待检查结束。

检查通过后会提示按键关闭窗口。若显示提交不匹配、工作区有修改或找不到依赖，先保留窗口中的错误信息，不要尝试重置或手改文件。

## 第二步：同学在 B 机启动 Edge worker

1. 在 B 机双击 `01_start_edge_on_B.bat`。
2. 等窗口出现 `worker_ready`。这个窗口必须保持打开，直到 A 机的执行结束。
3. 查看窗口打印的网络地址，选择 A 机能够访问的 Wi-Fi、以太网或 VPN 地址。把完整地址发给 A 机操作者，格式类似 `http://192.168.x.x:8010`。
4. 如果 Windows 防火墙询问，只允许当前可信的专用网络访问；不要关闭整个防火墙。

看到 `worker_ready` 只表示服务启动，不表示任务完成或验收通过。

## 第三步：在 A 机运行故障恢复实验

1. 确认 B 机 worker 窗口仍开着。
2. 在 A 机双击 `02_run_controller_on_A.bat`。
3. 程序询问 Edge 地址时，粘贴 B 机发来的完整地址并按 Enter。
4. 等待执行结束。过程中不要关闭窗口、不要按 Ctrl+C，也不要手动修改任务。
5. 结束后保留 A 机文件夹内生成的全部内容。

这次实验预期由独立注入器中止 Cloud worker；框架检测到失败后转到 B 机 Edge worker。第一阶段生成中间结果，第二阶段基于中间结果生成最终报告。

## 第四步：同学在 B 机导出日志

确认 A 机执行器已结束后，B 机双击 `03_export_edge_log_on_B.bat`。成功后会生成 `edge_return_<run-id>` 文件夹。将整个文件夹发回 A 机，同时保留 B 机原始文件 `edge_worker_raw.jsonl`。

如果导出器提示缺少本次任务的开始或完成事件，说明 B 没有完整执行该任务；保留原始日志和错误信息，不要自行编辑 JSONL 文件。

## 第五步：在 A 机做严格核验

1. 将 B 机回传的整个 `edge_return_<run-id>` 文件夹复制到 A 机。
2. A 机双击 `04_verify_returned_log_on_A.bat`。
3. 在提示处粘贴 `edge_worker_events.jsonl` 的完整文件路径，也可以从资源管理器把该文件拖进窗口，然后按 Enter。
4. 只有窗口明确显示 `PASS: strict cross-host verification` 才算真实双机复验通过。

严格核验会检查 A、B 的主机名和主机指纹不同、源码提交一致、run/task ID 一致、事件顺序正确、最终产物来自恢复后的中间结果，以及清单中的哈希匹配。

若看到 `FAIL`，不要改写结果或只截取通过的片段。保留 A 机完整 run 目录、B 机原始日志、回传目录和错误窗口信息，供后续定位。

## 通过后请交回的材料

A 机生成的完整目录位于：

```text
source/alternative-frame/v1.1-experimental/runs/dynamic_fault_injection/<run-id>/
```

请打包并交回整个 `<run-id>` 目录，不要只发截图。目录中应包括 `summary.json`、`acceptance_verification.json`、`manifest.json`、注入器与 Cloud/Edge 事件日志、框架 `events.jsonl` 和 `state.json`、`recovered_result.json`、`final_report.json`。

同时交回 B 机的 `edge_worker_raw.jsonl` 和 `edge_return_<run-id>` 整个回传目录。不要发送或修改 `test_config.json`。

## 常见情况

- **A 机连不上 B 机**：确认两机在同一可互访网络；重新核对 B 发来的 IP 和端口；检查防火墙是否允许专用网络访问。不要关闭防火墙或改用公网暴露服务。
- **A、B 显示相同主机身份**：多半是在同一台电脑上启动了两端，或 B 机运行的并非本次包中的 worker。严格验收要求两台真实不同的电脑。
- **只有 `worker_ready`，没有验收 PASS**：worker 启动不是验收结果；必须完成 A 机执行、B 机日志导出和 A 机严格核验。
- **运行失败或需要重跑**：不要复用本次 run ID 覆盖旧产物。保留失败目录与日志，再准备一个新 run ID 的复验包。

## 证据结论边界

即使严格双机核验通过，也只能说明这项受控 SHA-256 任务在外部 Cloud 进程被终止后完成了跨机回退、阶段续跑和最终产物核验。它不能单独证明边缘 LLM 推理、真实 API 长程任务成功，或比赛所有要求均已满足。
