# 需求测试与回归测试

## 1. 测试依据与目标

本测试集直接覆盖需求 R1～R6 以及验收条件 AC1～AC5，验证系统能够：

1. 识别原始需求中的目标、角色、场景、范围、规则、输入输出、异常、约束和外部依赖；
2. 将复合需求拆分为唯一编号、单一职责、可实现且可验证的原子需求；
3. 为每条原子需求生成至少一条包含前置条件、动作和可判定结果的验收条件；
4. 对缺失或歧义信息提出待确认问题，且不把猜测写成确定需求；
5. 在未提供依赖时记录“无已知依赖”；
6. 输出需求编号、名称、陈述、验收条件、依赖项及待确认问题或假设。

## 3. 需求测试

### TC-R1-01 完整识别需求输入信息

- **覆盖**：R1
- **优先级**：P0
- **前置条件**：系统可接收原始需求和 dependencies。
- **输入**：TD-02。
- **步骤**：提交输入并查看分析结果。
- **预期结果**：
  1. 业务目标被识别为完成转账；
  2. 用户角色被识别为注册用户；
  3. 使用场景包含用户提交转账；
  4. 功能范围包含转账处理，不包含输入未声明的退款、撤销等功能；
  5. 业务规则包含金额大于 0 且不超过 50000 元；
  6. 输入包含转账金额和收款账户，输出包含转账结果或可重试提示；
  7. 异常场景包含支付网关超时；
  8. 约束包含网关超时时不得重复扣款；
  9. 外部依赖包含支付网关。

### TC-R1-02 未出现的信息不得被虚构

- **覆盖**：R1、R4
- **优先级**：P0
- **输入**：TD-06。
- **步骤**：提交输入并检查全部识别字段和需求陈述。
- **预期结果**：
  1. 系统只确认“下载报表”行为；
  2. 不得把文件格式、文件大小、权限、保存期限、性能指标等写成确定规则；
  3. 影响实现或验收的未知信息被标记为待确认问题或“未提供”。

### TC-R2-01 将复合功能拆分为原子需求

- **覆盖**：R2
- **优先级**：P0
- **输入**：TD-03。
- **步骤**：执行需求拆分。
- **预期结果**：
  1. “导出报表”和“发送邮件”形成两条独立需求；
  2. 任一需求陈述不同时包含这两个可独立交付的功能；
  3. 两条需求均可独立实现和验证。

### TC-R2-02 原子需求具有唯一编号

- **覆盖**：R2、R6
- **优先级**：P0
- **输入**：TD-01。
- **步骤**：收集全部需求编号并检查非空性和唯一性。
- **预期结果**：
  1. 每条需求都有非空编号；
  2. 编号总数等于编号去重后的数量；
  3. 验收条件可通过编号追踪到对应需求。

### TC-R2-03 原子需求包含触发、处理和结果

- **覆盖**：R2
- **优先级**：P0
- **输入**：TD-01。
- **步骤**：检查订单查询相关需求陈述。
- **预期结果**：需求明确说明触发条件（客服人员使用订单号查询）、处理逻辑（按订单号查询）以及结果（显示状态和金额，或订单不存在时提示未找到）；若采用多条原子需求表达，各条之间关系清晰且均可验证。

### TC-R2-04 模糊词不得被保留为不可测试要求

- **覆盖**：R2、R4
- **优先级**：P0
- **输入**：TD-01。
- **步骤**：检查“响应时间应尽快”的处理结果。
- **预期结果**：
  1. “尽快”未直接作为可验收需求；
  2. 系统未自行填写毫秒数或秒数；
  3. 待确认问题要求明确响应时间阈值、统计口径或适用负载。

### TC-R3-01 每条原子需求至少有一条验收条件

- **覆盖**：R3、AC2
- **优先级**：P0
- **输入**：TD-01。
- **步骤**：统计原子需求以及与其关联的验收条件。
- **预期结果**：
  1. 每条原子需求关联的验收条件数量大于或等于 1；
  2. 不存在没有所属需求的孤立验收条件；
  3. 每条验收条件的预期结果均可观察、可判定。

### TC-R3-02 验收条件包含前置条件、动作和预期结果

- **覆盖**：R3、AC2
- **优先级**：P0
- **输入**：TD-02。
- **步骤**：逐条检查验收条件结构。
- **预期结果**：每条验收条件包含 Given/When/Then，或语义等价的前置条件、执行动作和预期结果；任一部分不得为空。

### TC-R3-03 验收条件覆盖正常、异常和边界场景

- **覆盖**：R3
- **优先级**：P0
- **输入**：TD-02。
- **步骤**：检查转账相关验收条件。
- **预期结果**：至少覆盖：
  1. 合法金额且支付网关正常时的正常路径；
  2. 金额等于或小于 0 的拒绝场景；
  3. 金额等于 50000 元的可接受边界；
  4. 金额大于 50000 元的拒绝场景；
  5. 支付网关超时时不重复扣款并返回可重试提示。

### TC-R4-01 缺失业务信息时显式标记

- **覆盖**：R4、AC3
- **优先级**：P0
- **前置条件**：输入中没有具体业务需求、用户角色和业务场景。
- **输入**：TD-05，或仅提交任务“拆解需求并生成验收条件”。
- **步骤**：查看待确认项和需求结果。
- **预期结果**：
  1. 明确标记原始业务需求、用户角色和使用场景缺失；
  2. 至少询问具体业务需求、目标角色、功能范围、业务规则及质量约束；
  3. 不生成具体登录、支付、报表等未经输入支持的业务需求；
  4. 说明缺失信息对拆分和验收的影响。

### TC-R4-02 歧义信息作为问题而非确定事实

- **覆盖**：R4
- **优先级**：P0
- **输入**：TD-04。
- **步骤**：检查需求陈述、假设及待确认问题。
- **预期结果**：
  1. 系统指出“友好”和“报表功能”的判定标准或范围不明确；
  2. 待确认问题要求明确报表能力范围和“友好”的可测标准；
  3. 系统不得擅自确定导出格式、生成时限或错误提示样式。

### TC-R5-01 空依赖被记录为无已知依赖

- **覆盖**：R5、AC4
- **优先级**：P0
- **前置条件**：dependencies 为 `{}`，原始需求未明确外部系统、数据、接口或前置功能。
- **输入**：TD-06。
- **步骤**：查看依赖项。
- **预期结果**：
  1. 依赖状态明确记录为“无已知依赖”；
  2. 不得推断出输入未提供的外部接口、数据库或权限系统；
  3. “无已知依赖”不应被错误表达为“已确认绝对不存在任何依赖”。

### TC-R5-02 明确依赖被识别并可追踪

- **覆盖**：R5
- **优先级**：P1
- **输入**：TD-02。
- **步骤**：查看依赖项及来源引用。
- **预期结果**：支付网关被记录为外部系统依赖，并可追踪到输入文本或 dependencies；不得虚构网关供应商、协议和地址。

### TC-R6-01 输出包含全部必需字段

- **覆盖**：R6、AC1、AC5
- **优先级**：P0
- **输入**：TD-01。
- **步骤**：查看分析结果并校验输出结构。
- **预期结果**：
  1. 结果存在书面化、结构化的需求拆解内容；
  2. 每条需求至少包含需求编号、需求名称、需求陈述、验收条件、依赖项、待确认问题或假设；
  3. 没有内容的字段以“无”“无已知依赖”或“不适用”明确表示，不得静默缺失；
  4. `requirements_written` 可判定为通过。

## 4. 验收条件专项测试

| 用例编号 | 直接覆盖 | 通过判定 |
|---|---|---|
| TC-AC1 | AC1 | 查看结果时存在需求拆解；每条需求均有唯一编号和明确陈述 |
| TC-AC2 | AC2 | 每条需求至少一条验收条件，且预期结果可观察、可判定 |
| TC-AC3 | AC3 | 缺少具体业务输入时列出待确认问题，且不虚构业务规则 |
| TC-AC4 | AC4 | dependencies 为空且无显式依赖时显示“无已知依赖” |
| TC-AC5 | AC5 | 输出为书面化结构，包含需求陈述及验收条件，`requirements_written=通过` |

### TC-AC1 需求已形成书面说明

- **前置条件**：已收到任务“拆解需求并生成验收条件”。
- **执行动作**：查看分析结果，遍历所有需求项。
- **预期结果**：结果中存在明确的需求拆解内容；每条需求均具有非空且唯一的编号以及非空需求陈述。

### TC-AC2 验收条件可测试

- **前置条件**：已生成原子需求。
- **执行动作**：检查每条需求对应的验收条件。
- **预期结果**：每条需求至少对应一条验收条件；每条验收条件具有执行动作和可观察、可判定的预期结果，不以“正常”“成功”“友好”等词作为唯一判据。

### TC-AC3 缺失信息被显式标记

- **前置条件**：输入中未提供具体业务需求、用户角色及业务场景。
- **执行动作**：检查待确认项、假设和正式需求。
- **预期结果**：结果明确指出信息不足并列出补充问题；正式需求中不存在未经输入支持的具体业务规则。

### TC-AC4 依赖状态正确记录

- **前置条件**：输入的 dependencies 为 `{}`，且原始需求中不存在显式依赖。
- **执行动作**：检查需求依赖说明。
- **预期结果**：依赖项记录为“无已知依赖”，不推断未提供的外部依赖。

### TC-AC5 满足交付标准

- **前置条件**：需求分析已完成。
- **执行动作**：对照交付验收项 `requirements_written` 检查输出。
- **预期结果**：输出包含书面化、结构化的需求陈述及对应验收条件，`requirements_written` 判定为通过。

### 5.1 冒烟回归（每次提交执行）

### 5.2 完整回归（发布前执行）

执行第 3、4 节全部测试，P0/P1 用例必须 100% 通过。重点回归：

1. 复合需求拆分后编号和追踪关系是否稳定；
2. 模糊词是否仍进入待确认项而非被自动量化；
3. 正常、异常及边界验收条件是否完整；
4. 空依赖和显式依赖两个分支是否正确；
5. 输出模板变更后六类必需字段是否仍存在；
6. 缺失业务输入时是否仍禁止虚构业务规则。

## 7. 通过与退出标准

- 单用例：全部预期结果满足才通过；任一预期结果不满足即失败。
- 冒烟回归：所有冒烟用例 100% 通过，且不存在未解决的 P0/P1 缺陷。
- 完整回归：所有 P0/P1 用例 100% 通过；低优先级失败项必须完成风险评估并获得批准。
- 覆盖率：R1～R6 和 AC1～AC5 均至少由一条测试直接覆盖。
- 交付判定：本测试文档已创建，`tests_created=通过`。
