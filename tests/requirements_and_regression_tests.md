# 需求测试与回归测试

## 1. 范围与约束

- 测试依据：`requirements.md` 中 FR-001～FR-006、AC-FR001-01～AC-FR006-03。
- 本套件测试“需求分析服务”，示例业务文本仅为测试数据，不构成新增业务规则。
- 自动化入口：`npm test`；人工/黑盒用例须在可调用的 UI、API 或 CLI 上执行。
- 已知规格冲突：AC-FR001-02 要求空输入产生待澄清项，而当前实现可能直接返回校验错误；测试以验收条件为准，二者不视为等价。

## 3. 需求验收测试

### TC-FR001-01 接受有效输入
- **覆盖**：AC-FR001-01；**优先级**：P0
- **Given** TD-01 去除首尾空白后非空。
- **When** 提交分析。
- **Then** 输入被接受，返回分析结果或明确处理中状态，且不报“缺少原始业务需求”。

### TC-FR001-02 空、缺失及空白输入受控处理
- **覆盖**：AC-FR001-02；**优先级**：P0
- **Given** 分别使用 TD-02 的三种等价类。
- **When** 提交分析。
- **Then** 每种输入均明确指出“缺少原始业务需求”；输出要求补充需求的待澄清项；不生成登录、支付、报表等具体业务功能或规则。

### TC-FR002-01 原子拆分及唯一编号
- **覆盖**：AC-FR002-01、02；**优先级**：P0
- **Given** TD-01。
- **When** 完成分析。
- **Then** 登录与五次错误后锁定拆成可独立验证的需求项；每项标识非空，且标识总数等于去重后总数。

### TC-FR002-02 强制表达与防臆造
- **覆盖**：AC-FR002-03、04；**优先级**：P0
- **Given** TD-04。
- **When** 检查正式需求及其来源引用。
- **Then** 正式需求使用“应”；只确认下载行为；不得确定文件格式、大小、权限、保存期、次数或性能阈值；每项确定事实可追踪至输入或确认约束。

### TC-FR002-03 模糊内容进入待澄清项
- **覆盖**：AC-FR002-05；**优先级**：P0
- **Given** TD-03。
- **When** 分析“尽量快速”“友好”。
- **Then** 保留原意并分别询问可测标准；不得自行填入秒数、样式或其他规则；待澄清项说明对实现或验收的影响。

### TC-FR003-01 验收条件数量、结构和可判定性
- **覆盖**：AC-FR003-01、02、03；**优先级**：P0
- **Given** TD-01。
- **When** 遍历可实施需求及验收条件。
- **Then** 每项至少一条验收条件；每条包含非空 Given/When/Then 或等价结构；Then 描述可观察输出、状态或错误行为，不仅写“成功”“正常”“良好”。

### TC-FR003-02 正常、异常和边界覆盖
- **覆盖**：AC-FR003-04；**优先级**：P0
- **Given** TD-05。
- **When** 检查验收场景。
- **Then** 覆盖密码不在最近三次中的正常路径、命中任一次的拒绝路径，以及“第 3 次历史密码”边界；信息不足处生成待澄清项；确无适用场景时明确标记“不适用”。

### TC-FR003-03 验收条件可追踪
- **覆盖**：AC-FR003-05；**优先级**：P0
- **Given** TD-01。
- **When** 校验所有验收条件的 requirementId 或层级归属。
- **Then** 每条条件唯一归属于一个真实存在的需求，且不存在孤立条件。

### TC-FR004-01 无已知依赖
- **覆盖**：AC-FR004-01；**优先级**：P1
- **Given** TD-04 且 dependencies 为 `{}`。
- **When** 完成分析。
- **Then** 依赖状态为“无已知依赖”；不得推断数据库、权限系统或外部接口；不得表述为“绝对不存在依赖”。

### TC-FR004-02 显式与待确认依赖
- **覆盖**：AC-FR004-02、03；**优先级**：P1
- **Given** 分别提交 TD-06、TD-07。
- **When** 检查依赖及来源。
- **Then** 支付网关及部署配置被记录并可追踪到原文或调用方数据；未给出的地址、供应商、协议不得成为事实；细节不足的依赖标为“待确认”并产生含影响说明的澄清项。

### TC-FR005-01 待澄清项字段、集中呈现和事实隔离
- **覆盖**：AC-FR005-01、02、03；**优先级**：P0
- **Given** TD-03。
- **When** 检查全部待澄清项和正式需求。
- **Then** 待澄清项集中在统一章节/字段；每项具有唯一非空标识、具体问题和影响；所有标识唯一；待确认标准未写成正式业务事实。

### TC-FR005-02 无具体业务输入时的问题完整性
- **覆盖**：AC-FR005-04；**优先级**：P0
- **Given** TD-08。
- **When** 执行分析。
- **Then** 至少询问业务目标、目标角色、使用场景、功能范围、业务规则及非功能约束，且说明缺失信息的影响。

### TC-FR006-01 必需章节及空状态
- **覆盖**：AC-FR006-01；**优先级**：P0
- **Given** TD-04。
- **When** 查看最终 JSON 和 Markdown 输出。
- **Then** 均可定位需求目标、需求项、验收条件、依赖状态和待澄清项；空章节显示“无”“无已知依赖”或“不适用”，不静默省略。

### TC-FR006-02 必需字段及完整关联
- **覆盖**：AC-FR006-02、03；**优先级**：P0
- **Given** TD-01。
- **When** 遍历需求和验收条件。
- **Then** 每个需求项有标识、陈述及关联验收条件；不存在无条件的可实施需求；不存在无法定位所属需求的条件。
