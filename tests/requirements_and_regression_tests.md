# 需求测试与回归测试

## 1. 测试目标
验证需求拆解系统满足 `requirements.md` 中 FR-001～FR-005 的全部验收条件，并通过回归测试确保后续变更不会破坏以下核心能力：

- 正确接收或拒绝原始需求输入；
- 将需求拆分为单一职责、唯一标识、无臆造的需求项；
- 生成可测试、可观察、可追踪的验收条件；
- 正确记录依赖、假设和待澄清项；
- 输出完整的结构化结果。

## 2. 测试范围与说明

- 测试依据：`requirements.md`。
- 当前未提供具体业务系统实现、接口定义或运行方式，因此本文提供可直接执行的黑盒测试设计，但暂不绑定具体 UI、API 或命令行步骤。
- 测试输入中的示例仅用于验证“需求拆解系统”的通用行为，不代表新增业务规则。
- 实际执行时，应将“提交”替换为被测系统对应的 UI 操作、API 请求或命令行调用。

## 4. 需求测试用例

### RT-FR001-01 接受非空原始需求

- **关联需求**：FR-001
- **关联验收条件**：非空需求被接受并开始分析。
- **优先级**：P0
- **前置条件**：被测系统可用。
- **输入**：TD-001。
- **步骤**：
  1. 提交 TD-001。
  2. 观察系统响应及输出。
- **预期结果**：
  1. 系统接受输入，不返回“缺少原始需求”。
  2. 系统进入分析流程并输出分析结果或明确的处理中状态。

### RT-FR001-02 拒绝空字符串且不得臆造需求

- **关联需求**：FR-001
- **关联验收条件**：空输入时指出缺少原始需求，且不得臆造具体业务需求。
- **优先级**：P0
- **前置条件**：被测系统可用。
- **输入**：TD-002。
- **步骤**：提交空字符串。
- **预期结果**：
  1. 系统明确指出缺少原始需求。
  2. 输出中不出现未经输入支持的业务功能、业务规则或验收标准。
  3. 如系统生成待澄清项，应要求提供原始业务需求并说明影响。

### RT-FR001-03 拒绝仅含空白字符的输入

- **关联需求**：FR-001
- **关联验收条件**：仅包含空白字符的输入按空输入处理。
- **优先级**：P0
- **输入**：TD-003。
- **步骤**：提交仅包含空格、换行和制表符的输入。
- **预期结果**：结果与 RT-FR001-02 一致；系统不得将空白字符识别为有效需求。

### RT-FR002-01 将复合需求拆分为单一职责需求项

- **关联需求**：FR-002
- **关联验收条件**：每个需求项只描述一个可验证行为、规则或质量约束。
- **优先级**：P0
- **输入**：TD-001。
- **步骤**：提交输入并检查拆解结果。
- **预期结果**：
  1. “邮箱和密码登录”与“连续错误 5 次锁定账户”被拆分为不同需求项。
  2. 不存在同时要求登录与锁定两个行为的单一需求项。
  3. 每个需求项均可独立验证。

### RT-FR002-02 每个需求项具有唯一标识符

- **关联需求**：FR-002
- **关联验收条件**：每个需求项包含唯一标识符。
- **优先级**：P0
- **输入**：TD-001。
- **步骤**：收集全部拆解需求项的标识符并进行非空与去重检查。
- **预期结果**：
  1. 每个需求项均有非空标识符。
  2. 标识符数量等于去重后的标识符数量。

### RT-FR002-03 使用强制性、可量化表述并标记模糊内容

- **关联需求**：FR-002
- **关联验收条件**：使用“应”描述强制要求；模糊表述应标记为待澄清项。
- **优先级**：P0
- **输入**：TD-004。
- **步骤**：提交输入并检查需求项与待澄清项。
- **预期结果**：
  1. 正式需求陈述使用明确的强制性表达。
  2. “尽量快速”和“友好”未被擅自转换为具体数值或判定标准。
  3. 系统将报表生成时限、错误提示判定标准记录为待澄清项，并说明对验收的影响。

### RT-FR002-04 不引入输入中不存在的业务规则

- **关联需求**：FR-002
- **关联验收条件**：不得引入无法从原始需求或确认约束推导出的业务规则。
- **优先级**：P0
- **输入**：TD-006。
- **步骤**：提交输入并检查全部需求项。
- **预期结果**：
  1. 输出可包含“下载报表”行为。
  2. 输出不得擅自规定报表格式、文件大小、下载权限、保存期限、下载次数或性能指标。
  3. 未确认但影响实施或验收的信息应进入待澄清项，而不是作为事实写入需求。

### RT-FR003-01 每个需求项至少有一条可验证验收条件

- **关联需求**：FR-003
- **关联验收条件**：每个可实施需求项至少关联一条可执行或人工可验证的验收条件。
- **优先级**：P0
- **输入**：TD-001。
- **步骤**：统计需求项及其关联的验收条件。
- **预期结果**：
  1. 每个可实施需求项的验收条件数量不少于 1。
  2. 不存在孤立、无归属的验收条件。

### RT-FR003-02 验收条件包含前置条件、触发和预期结果

- **关联需求**：FR-003
- **关联验收条件**：验收条件具备 Given/When/Then 或等价可测试表达。
- **优先级**：P0
- **输入**：TD-006。
- **步骤**：检查生成的每条验收条件。
- **预期结果**：每条验收条件均能明确回答：在什么条件下、执行什么操作或发生什么事件、应观察到什么结果。

### RT-FR003-03 覆盖正常、关键异常和边界场景

- **关联需求**：FR-003
- **关联验收条件**：覆盖正常路径、关键异常路径和边界条件；无相关场景时明确标记不适用。
- **优先级**：P0
- **输入**：TD-007。
- **步骤**：提交输入并检查验收条件集合。
- **预期结果**：
  1. 包含新密码不在最近 3 次密码中的正常场景。
  2. 包含新密码与最近 3 次中任一次相同的拒绝场景。
  3. 覆盖“第 3 次历史密码”这一边界；若更细的历史定义无法从输入确定，应记录待澄清项。
  4. 对确实不存在的场景，输出明确标记“不适用”，而非遗漏且不说明。

### RT-FR003-04 预期结果可观察且有明确判定标准

- **关联需求**：FR-003
- **关联验收条件**：预期结果不得仅使用“成功”“正常”“性能良好”等无标准表述。
- **优先级**：P0
- **输入**：TD-001。
- **步骤**：检查所有预期结果文本。
- **预期结果**：
  1. 预期结果描述可观察的系统状态、输出、错误信息类别或行为。
  2. 不存在仅以“成功”“正常”“良好”作为唯一判定依据的验收条件。

### RT-FR003-05 验收条件可追踪到对应需求项

- **关联需求**：FR-003
- **关联验收条件**：每条验收条件能够追踪到对应需求项。
- **优先级**：P0
- **输入**：TD-001。
- **步骤**：检查验收条件中的需求标识引用或层级归属关系。
- **预期结果**：每条验收条件均可唯一确定其所属需求项；引用的需求标识真实存在。

### RT-FR004-01 无依赖时标记“无已知依赖”

- **关联需求**：FR-004
- **关联验收条件**：输入声明依赖为空且未识别到额外依赖时，标记“无已知依赖”。
- **优先级**：P1
- **输入**：TD-008。
- **步骤**：提交输入并检查依赖章节。
- **预期结果**：依赖章节明确显示“无已知依赖”或语义完全等价的明确结论，不得凭空新增外部依赖。

### RT-FR004-02 识别并记录明确的外部依赖

- **关联需求**：FR-004
- **优先级**：P1
- **输入**：TD-005。
- **步骤**：提交输入并检查依赖章节。
- **预期结果**：
  1. 支付网关被记录为外部系统依赖。
  2. 部署环境提供网关地址被记录为配置或部署依赖。
  3. 不得将输入未声明的支付渠道、协议或供应商作为既定事实。

### RT-FR004-03 未确认信息进入待澄清项而非需求事实

- **关联需求**：FR-004
- **关联验收条件**：影响范围或验收的未确认信息记录为待澄清项。
- **优先级**：P0
- **输入**：TD-004。
- **步骤**：检查需求、依赖、假设及待澄清项。
- **预期结果**：
  1. 所有影响范围或验收但未确认的信息集中记录为待澄清项。
  2. 每项均说明其对范围或验收结果的影响。
  3. 未确认信息不作为已确定规则写入正式需求。

### RT-FR005-01 输出包含全部必需章节和字段

- **关联需求**：FR-005
- **关联验收条件**：输出需求目标、需求项、验收条件、依赖、待澄清项；需求项至少包含标识、陈述、验收条件。
- **优先级**：P0
- **输入**：TD-001。
- **步骤**：提交输入并检查输出结构。
- **预期结果**：
  1. 输出包含需求目标、需求项、对应验收条件、依赖、待澄清项。
  2. 每个需求项包含需求标识、需求陈述及至少一条验收条件。
  3. 章节无内容时应给出“无”或“不适用”等明确状态，不得静默缺失。

### RT-FR005-02 所有需求项均关联验收条件

- **关联需求**：FR-005
- **关联验收条件**：所有需求项至少关联一条验收条件。
- **优先级**：P0
- **输入**：TD-001。
- **步骤**：遍历输出中的全部需求项。
- **预期结果**：每个需求项关联的验收条件数量大于等于 1。

### RT-FR005-03 待澄清项集中列出并说明影响

- **关联需求**：FR-005
- **关联验收条件**：所有待澄清内容集中列出，并说明对范围或验收的影响。
- **优先级**：P0
- **输入**：TD-004。
- **步骤**：检查待澄清内容的位置和字段。
- **预期结果**：
  1. 待澄清内容可在统一章节中完整检索。
  2. 每个待澄清项包含问题描述及影响说明。
  3. 正式需求中的模糊内容均能在待澄清项中找到对应记录。

### RT-CURRENT-01 原始业务需求缺失时保持受控输出

- **关联章节**：当前输入分析、Q-001、任务级验收结果
- **优先级**：P0
- **输入**：仅提交任务名称“拆解需求并生成验收条件”，不提供业务需求。
- **步骤**：执行分析。
- **预期结果**：
  1. 系统明确说明缺少原始业务需求。
  2. 系统不生成具体业务功能或业务规则。
  3. 系统生成要求补充原始业务需求的待澄清项。
  4. 系统说明缺失信息会阻碍确定功能范围、异常场景及业务验收标准。
  5. 若未识别额外依赖，记录“无已知依赖”。

## 5. 回归测试套件

### 5.1 冒烟回归（每次提交执行）

| 用例 | 回归目的 |
|---|---|
| RT-FR001-01 | 有效输入仍可进入分析 |
| RT-FR001-02 | 空输入保护及防臆造能力未失效 |
| RT-FR002-01 | 复合需求仍能拆分 |
| RT-FR002-02 | 唯一标识规则未失效 |
| RT-FR003-01 | 需求与验收条件完整关联 |
| RT-FR003-05 | 追踪关系未失效 |
| RT-FR005-01 | 输出结构完整 |
| RT-CURRENT-01 | 缺少业务输入时保持受控行为 |

### 5.2 完整回归（发布前执行）

执行第 4 节全部用例，重点检查：

1. 空输入和空白输入处理；
2. 单一职责拆解与唯一标识；
3. 模糊词、未知信息及防臆造处理；
4. 正常、异常、边界验收条件覆盖；
5. 依赖识别和“无已知依赖”分支；
6. 输出完整性和双向可追踪性。

### 5.3 缺陷修复后的定向回归

| 变更或缺陷类型 | 必跑用例 |
|---|---|
| 输入校验变更 | RT-FR001-01～03、RT-CURRENT-01 |
| 拆解算法或提示词变更 | RT-FR002-01～04、RT-FR003-01～05 |
| 验收条件生成逻辑变更 | RT-FR003-01～05、RT-FR005-02 |
| 依赖/假设识别变更 | RT-FR004-01～03、RT-CURRENT-01 |
| 输出模板或格式变更 | RT-FR002-02、RT-FR003-05、RT-FR005-01～03 |

## 7. 通过/失败标准

- **单用例通过**：全部预期结果均满足；任一预期结果不满足则该用例失败。
- **冒烟回归通过**：冒烟用例 100% 通过，且不存在 P0/P1 阻塞缺陷。
- **完整回归通过**：P0、P1 用例 100% 通过；其余失败项须完成风险评审。
- **需求覆盖通过**：FR-001～FR-005 每项至少被一个测试覆盖；本测试集已实现全部验收条件覆盖。
